# 要件定義・設計スキル

## 成果物と流れ

| 段階 | 成果物 | パス |
|------|--------|------|
| ヒアリング・言語化 | ヒアリングシート | `docs/01_ヒアリングシート.md` |
| 要件定義 | 要件定義書 | `docs/02_要件定義書.md` |
| 基本設計 | 基本設計書 | `docs/03_基本設計書.md` |
| 詳細設計 | 詳細設計書 | `docs/04_詳細設計書.md` |

**流れ**: ヒアリングシートで「作りたいこと」を言語化・合意 → 要件定義書で目的・機能・非機能を確定 → 基本設計書で構成・画面/API・データの流れを決める → 詳細設計書で機能単位の処理・データ構造・画面項目を書く。

## 各段階のチェックリスト

### ヒアリング（01）

- [ ] 誰が使うか（利用者）を特定したか
- [ ] 何のスケジュール（対象）を扱うか明確か
- [ ] どのように更新するか（手順・画面・権限）のイメージがあるか
- [ ] 困っていること・やりたいことの具体例を 1 つ以上書いたか
- [ ] 用語の意味をお客様と揃えたか（用語集のたたき台）

### 要件定義（02）

- [ ] プロジェクト目的が 1 文で書かれているか
- [ ] ユーザー種別と利用シーンが書かれているか
- [ ] 機能一覧（必須/任意の区別）があるか
- [ ] 非機能要件（性能・セキュリティ・運用）に触れているか
- [ ] 用語集があり、未決定は「要確認」と明記しているか
- [ ] 検討・提案メモに不足・リスク・改善案を追記したか

### 基本設計（03）

- [ ] システム構成図（クライアント・サーバ・外部連携）があるか
- [ ] 画面一覧または API 一覧があるか
- [ ] 主要なデータの流れが説明されているか
- [ ] スケジュール更新の想定パターンが 1 つ以上あるか
- [ ] 検討・提案メモを更新したか

### 詳細設計（04）

- [ ] 機能単位で処理フローが書かれているか
- [ ] データ構造（項目・型・必須/任意）が定義されているか
- [ ] 画面がある場合は項目一覧があるか
- [ ] 検討・提案メモを更新したか

## 提案メモの書き方

各ドキュメント末尾の「検討・提案メモ」には次を書く:

- **前提の抜け**: まだ決まっていない前提や、確認すべきこと
- **リスク**: 実現の難しさ、スケジュール・コストへの影響
- **より良い案**: 代替案・拡張案・運用で補う案

お客様が「十分か」を自己判断できるよう、提案は選択肢として示し、**完了の主導権はお客様**に置く。

## テンプレートとの対応

- 新規で要件・設計を書くときは、上記 `docs/01_〜04_` のファイルをベースにし、項目を埋めていく。
- 既存のたたき台がある場合は、ヒアリング・合意内容で上書きし、未決定は「要確認」のままにしない（合意 or 意図的な先送りを明記）。

## 実行時の注意

- ドキュメントを編集する前に、**何をどのファイルに書くか**を簡潔に説明し、許可を得てから実行する。
- 一度に大きな変更より、**段階的な追記・修正**を心がける（認知負荷の配慮）。
- タスクの追加・進捗変更時は、プロジェクトの **todo.md** を [.cursor/rules/todo.mdc](.cursor/rules/todo.mdc) の形式に従って更新する。
